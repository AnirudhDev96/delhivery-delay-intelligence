# Delhivery Last-Mile Delay Intelligence Pipeline

This project answers three questions for a regional operations team:

- How many hours will a parcel actually take to deliver?
- Which parcels are likely to miss their promised time (Express 36 hours, Standard 60 hours, Economy 96 hours)?
- Which of the 24 hubs need which playbook?

The answers are built as one chain. Cleaning and features from Part A feed the regression in Part B and the classifier in Part C. Part D groups hubs into segments, and `predict_delay.py` combines the classifier with those segments to produce an action list for a new batch of parcels.

The shipment records are synthetic. They come from `generate_data.py`. No real Delhivery data is used.

```
generate_data.py          -> data/hubs.csv, data/raw_shipments.csv, data/new_shipments.csv
src/shipment_prep.py      -> PROMISED_HOURS, FEATURES, clean_shipments(), build_features()
part_a_clean_eda.py       -> data/modelling_table.csv and outputs/part_a_*.csv
part_b_regression.py      -> outputs/part_b_*.csv
part_c_classification.py  -> outputs/part_c_*.csv
part_d_segments.py        -> hub profiles, segments and the tier mismatch list
package_model.py          -> models/* and outputs/part_d_reload_check.csv
predict_delay.py          -> outputs/new_shipment_actions.csv
```

## How to run

From a fresh clone, at the repository root:

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python generate_data.py            # prints: 24 1224 48
python part_a_clean_eda.py
python part_b_regression.py
python part_c_classification.py
python part_d_segments.py
python package_model.py
python predict_delay.py
```

`models/delay_model.pkl` is regenerated by running `python package_model.py`. The pickle in the repo will only load reliably on the scikit-learn version pinned in `requirements.txt` (`scikit-learn==1.9.1`). If the installed versions differ, run `package_model.py` again instead of loading the committed pickle. That is also what a grader should do.

`predict_delay.py` is deterministic. Running it twice produces a byte-identical `outputs/new_shipment_actions.csv`.

## Data findings

After removing 24 exact duplicate rows from the 1,224-row export, 1,200 shipments remain. 278 of them are delayed, a rate of 0.2317 (`outputs/part_a_checks.csv`).

Express is the service that misses its promise most often. 119 of 243 Express parcels were delayed (rate 0.4897). Standard is 0.2056 (132 of 642) and Economy is 0.0857 (27 of 315). Express also has the tightest promise, 36 hours, so the same extra hours that a Standard parcel can absorb will push Express over the line.

Delay rate also climbs with hub tier: 0.0400 at Tier 1 (16 of 400), 0.2150 at Tier 2 (86 of 400) and 0.4400 at Tier 3 (176 of 400). Tier 3 hubs are delayed eleven times as often as Tier 1.

The same pattern shows up by distance (`outputs/part_a_delay_by_group.csv`). The 0-200 km band is almost always on time (delay rate 0.0219). That rises to 0.1368 at 201-400 km, 0.4364 at 401-600 km, and 0.8523 beyond 600 km (75 of 88 parcels).

Ranking the numeric columns in `outputs/part_a_correlations.csv` by absolute correlation with `delivery_hours` (and leaving `delivery_hours` itself out), the three strongest are `promised_hours` (0.8372), `distance_km` (0.4013) and `n_stops` (0.3247). For reference, `corr(delivery_hours, distance_km)` is 0.4013 and `corr(is_delayed, distance_km)` is 0.5455.

`declared_value_inr` was log-transformed because the filled column is right-skewed. The mean is 1533.0542 while the median is 1121.5. After taking the natural log, the mean (7.0277) and median (7.0224) sit almost on top of each other, so a handful of high-value parcels no longer stretch the scale.

A few other cleaning notes from the same checks file: 36 missing distances, 24 missing weights plus 5 scanner-fault weights of 999 kg, 12 missing declared values, and 18 missing payment modes (filled as "Unknown"). Twelve different `service_type` strings collapse to the three expected spellings after strip and title case. Gaps were filled with the historical medians: 314.95 km, 1.83 kg and 1121.5 INR. Delivery hours have Q1 43.255 and Q3 72.5625; the 1.5 IQR bounds are -0.7063 and 116.5238, and one outlier sits outside them (it was kept).

## Model results (regression)

The modelling table was split 840 / 180 / 180 (`outputs/part_b_checks.csv`). A `StandardScaler` fitted only on the training rows has a largest absolute column mean of 0.0 on train and 0.2187 on test, which is what you would expect if the test rows were never used to fit the scaler.

Predicting the training-set mean for every validation parcel gives R2 of -0.0212 and RMSE of 18.8552 hours. A negative R2 just means that constant guess is slightly worse than predicting the validation mean. Anything useful has to beat that baseline.

On the validation set, linear regression is the best of the four candidates (RMSE 4.8912, R2 0.9313). Gradient boosting is close behind (4.9165, 0.9306), then random forest (5.468, 0.9141) and a depth-6 decision tree (6.2796, 0.8867). The linear model was scored once on the held-out test rows: RMSE 4.5235, R2 0.9493. That high R2 is not surprising here. The generator is mostly an additive formula, so a linear model can recover it well.

The tree-depth table (`outputs/part_b_tree_depth.csv`) shows the usual bias-variance pattern. Depths 1 to 3 are high bias: train and validation error are both high and close together. At depth 1 the gap is about 0.50 hours (train 11.6334, val 12.1324). Depths 8, 12 and unlimited are high variance: training error keeps falling while validation error rises. With no depth limit the tree memorises the training set (train RMSE 0.0) and validation RMSE jumps to 7.789. Depth 6 has the lowest validation RMSE (6.2796), so that is the tree used in the comparison.

For gradient boosting, a learning rate of 0.1 is clearly the best of the three tried (validation R2 0.9306). 0.01 is too conservative; 100 small steps underfit (R2 0.7127). 1.0 overshoots, with each tree over-correcting the last one (R2 0.844).

Five-fold CV on the 1,020 training-plus-validation rows, using one shared `KFold(n_splits=5, shuffle=True, random_state=42)`, ranks the two best models the other way around (`outputs/part_b_cv.csv`): gradient boosting 0.9352 (std 0.0044) vs linear regression 0.9261 (std 0.0048). I would ship gradient boosting. The CV gap is larger than the fold-to-fold spread, while linear regression only won the single 180-row validation split, and only by 0.025 hours of RMSE. The test row in `outputs/part_b_metrics.csv` is still for linear regression, because that is the validation winner the script is required to score.

## Model results (classification)

The classifier uses the same 840 / 180 / 180 split, this time stratified on `is_delayed`, so the delayed counts are 195 / 42 / 41.

A blind baseline that marks every parcel on time has accuracy 0.7667 on validation (TN 138, FN 42). That number is just 1 minus the delay rate. Recall is 0, so the model never catches a delayed parcel and is useless for operations even though the accuracy looks respectable.

The three trained models all beat that accuracy (0.8833 to 0.9056). At the default 0.5 threshold, logistic regression has validation F1 0.8046, the best decision tree (depth 6) has 0.747, and the default random forest has 0.7848 (`outputs/part_c_models.csv`).

The five bookkeeping columns (`label_print_batch`, `scanner_build_no`, `tape_roll_no`, `sticker_serial_mod`, `shelf_slot_no`) take about 0.2245 of the forest's importance when all 17 features are used (0.046 + 0.0374 + 0.0476 + 0.0499 + 0.0436). The forest spreads some weight onto columns that should not matter. By F-score they all sit outside the top 7: the strongest noise column is `label_print_batch` at 4.5847 (rank 8). The top seven F-scores are `distance_km`, `hub_tier`, `hub_daily_capacity`, `n_stops`, `promised_hours`, `rain_flag` and `sale_event_flag`, and the weakest of those is still 36.7281.

Selecting features before the forest helps. Validation F1 by k is 0.6988 (k=5), 0.8333 (k=7), 0.7857 (k=10), 0.8049 (k=12) and 0.7848 (k=17). Seven columns is the peak. Dropping to five throws away useful signal; adding the noise columns back does not help.

Tuning on those same seven columns did not beat the untuned forest. Grid search (27 candidates, 135 fits) reached a best CV accuracy of 0.8952 but only 0.775 validation F1. Randomized search (9 candidates, 45 fits) was 0.8905 and 0.7848. The default forest (`n_estimators=100`, no depth limit, `min_samples_leaf=1`) had validation F1 0.8333. Part of that is the search scoring on accuracy rather than F1. The rest is the size of the validation set: with only 42 delayed parcels, one or two different calls move F1 by several points, so small gaps are mostly noise. The final model is therefore `SelectKBest(k=7)` followed by that default forest.

The operations rule is to take the highest threshold whose validation recall is at least 0.80, because missing a delayed parcel costs more than an extra customer call. From `outputs/part_c_thresholds.csv` that threshold is 0.5 (precision 0.7955, recall 0.8333). At 0.6, recall falls to 0.7619, so 0.5 is as high as we can go. Lower thresholds buy more recall at the cost of more calls; at 0.3, recall is 0.9286 but precision drops to 0.6964.

The same model and threshold were scored once on the test set (`outputs/part_c_final_test.csv`): precision 0.6889, recall 0.7561, F1 0.7209 (TP 31, FN 10, FP 14). Test recall is lower than the 0.8333 seen on validation. That is expected. There are only 41 delayed test parcels, so each miss costs about 0.024 recall, and the threshold was chosen on the validation set.

## Operations recommendation

Nine hubs fall in the Escalate segment, with an average delay rate of 0.4600 (`outputs/segment_profile.csv`). Individual rates from `outputs/hub_profile.csv`:

- HUB13 Nagpur: 0.46
- HUB15 Kochi: 0.36
- HUB17 Patna: 0.46
- HUB18 Ranchi: 0.38
- HUB19 Guwahati: 0.62
- HUB20 Raipur: 0.48
- HUB21 Bhubaneswar: 0.40
- HUB23 Siliguri: 0.44
- HUB24 Agartala: 0.54

The Watch segment has 8 hubs and an average delay rate of 0.1550. Standard has 7 hubs and 0.0257.

Four hubs do not behave like their official tier (`outputs/tier_vs_segment_mismatch.csv`):

- HUB07 Kolkata is labelled Tier 1 but clusters with Watch.
- HUB13 Nagpur is labelled Tier 2 but clusters with Escalate.
- HUB15 Kochi is labelled Tier 2 but clusters with Escalate.
- HUB22 Dehradun is labelled Tier 3 but clusters with Watch.

Playbooks and staffing should follow the measured segment, not the tier tag. The tier can stay as an administrative label, but these four should be reviewed.

The alert threshold is 0.5. On the test set, about 7 of every 10 flagged parcels are actually delayed (precision 0.6889) and about 7.5 of every 10 delayed parcels are caught (recall 0.7561).

Of the 48 new parcels, 8 are flagged. 6 of those sit in Escalate hubs and should go to the hub manager. The other 2 get a proactive customer call. The remaining 40 need no action.

K = 3 is kept even though the across-to-within ratio in `outputs/part_d_separation.csv` keeps rising: 2.8940 at K=2 (sizes 15-9), 5.3928 at K=3 (9-8-7), 6.3047 at K=4 (8-7-5-4) and 6.8866 at K=5 (8-7-4-3-2). Operations only runs three playbooks, and both K=4 and K=5 produce a cluster smaller than 6 hubs, which is too thin to justify its own playbook. K=3 is where the ratio jumps the most while the groups stay balanced.

## Production plan

A few production habits already live in this repo:

- Accuracy: the held-out numbers in `outputs/part_c_final_test.csv` and the test row of `outputs/part_b_metrics.csv`.
- Reliability: `predict_delay.py` fills missing fields with the stored medians in `models/impute_values.csv`, so a blank distance or weight does not crash scoring.
- Reproducibility: `random_state=42` is fixed throughout, versions are pinned in `requirements.txt`, and the generator and scoring script are deterministic.
- Consistency: training and scoring both call `clean_shipments` and `build_features` from `src/shipment_prep.py`, and `models/feature_order.csv` locks the column order.
- Maintainability: shared constants and cleaning live in one module; each part is a single script.
- Monitorability: `outputs/new_shipment_actions.csv` writes the probability, flag and action for every new parcel, so later outcomes can be joined back.
- Performance was not a bottleneck here. A 100-tree forest on 7 columns scores the 48 new parcels in well under a second.

Things I would watch once this was live:

- Weekly delayed share among delivered parcels. Alert if it stays outside 0.18-0.29 for two weeks (the modelling table rate is 0.2317).
- Weekly share of parcels flagged. Alert if that moves more than 8 points away from the validation flag rate (44 of 180, about 0.24, at threshold 0.5).
- Recall on parcels whose outcome is now known. Alert if a rolling 4-week recall drops below 0.70.
- Precision on those same parcels. Alert below 0.55, which would mean the call centre is chasing too many false alarms.
- Input drift: mean `distance_km` or the share of Express shifting by more than 15%, or a missing-value rate above 5% on any column used for scoring.

I would retrain monthly on the latest 90 days of delivered parcels, re-run Parts A to D, and only promote the new model if test recall at the chosen threshold is at least 0.75. The 15-28 September sale (`sale_event_flag = 1`) adds extra hours and hits Express hardest, so sale weeks should be compared with earlier sale events, not with ordinary weeks. Retraining on a sale fortnight alone would teach the model the wrong baseline. Drift in this setting would look like a hub suddenly handling more parcels than its capacity, lanes getting longer or stop counts rising (the hub sliding into a worse segment), a new service type or spelling appearing, or the delayed share rising when there is no sale flag.

## Limitations

The data is synthetic. The target is generated from a mostly additive formula, which is why the regression R2 sits around 0.93 and why the feature ranking is so clean. Real shipment data would be noisier.

The test set has only 41 delayed parcels and the validation set has 42. One extra miss changes recall by about 0.024, so the precision and recall figures can move by several points just from sampling.

The threshold and the choice of the default forest were decided on a single validation split. A different split could pick another threshold or prefer one of the tuned forests. Selecting the threshold inside cross-validation would be more stable.

Each hub profile is based on 50 parcels over about 90 days. Borderline hubs such as HUB14 or HUB22 could change segment if more history were available.

Finally, the regression model I would actually ship (gradient boosting, from the CV ranking) is not the one whose test score is reported. The reported test R2 of 0.9493 is for linear regression, the validation winner.
